# kffi X11 Bindings Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add reproducibly generated JVM FFM bindings for the low-level X11 surface used by `poc-koreos`.

**Architecture:** Add a JVM-only `kffi-x11` module parallel to `kffi-wayland`. A Docker generator invokes the pinned kextract submodule at commit `9252fb417ea91dae882a6a9e9d06ab672c50adc3` against Linux X11 headers and writes declarations into the module's `generated` package. Complex Xlib records remain generated pointer APIs; generated `KffiXEventStorage` and `XShmSegmentInfoCompat` are the only compatibility layouts. Tests exercise reflected generated functions, those layouts, and a Linux-only no-server native smoke path.

**Tech Stack:** Kotlin Multiplatform, Gradle 9.7, JDK 25 Panama FFM, Docker, LLVM/libclang 18, X11 development headers, kextract JVM-direct generation.

**Spec:** `docs/superpowers/specs/2026-08-20-kffi-x11-design.md`

## Global Constraints

- The parent repository must pin `third_party/kextract` to `9252fb417ea91dae882a6a9e9d06ab672c50adc3`.
- Generated source must be produced by kextract; do not handwrite FFM descriptors or native struct/union offsets.
- The module is JVM-only and targets JDK 25, matching `kffi-wayland`.
- X11 availability must not be required by non-native tests.
- Raw layouts for complex Xlib records are out of scope; preserve generated `MemorySegment` pointer APIs and validate only the C compatibility shims against native headers.
- Pin the Docker base image by digest and use an explicit `linux/amd64` or `linux/arm64` platform selected from the host architecture; the declared Ubuntu packages are supplied at image-build time, not APT-snapshot pinned.
- Do not port higher-level `kadre-x11` windowing or event-loop code in this change.
